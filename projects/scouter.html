사용 기술

구체적인 기술 스택(언어·프레임워크·DB 등)은 아직 채워지지 않았습니다 — 알려주시면 선택 이유와 함께 정리해서 넣겠습니다.

주요 기능 / 담당 부분

Scouter의 주요 기능은 다음과 같습니다.

  • 서류 평가 — 지원자 서류에 대한 평가 및 결과 관리
  • 면접 평가 — 면접관의 평가 입력과 동료 평가 확인
  • 메일 보내기 — 템플릿 기반 지원자 안내 메일 발송
  • 면접 일정 시간표 — 면접 일정 조율 및 관리

이 중 면접 평가 도메인 기능을 백엔드로 개발했고, 제가 담당하지 않은 영역에 대해서는 프론트엔드 CS 대응과 리팩토링을 함께 맡았습니다. 리크루팅뿐 아니라 향후 동아리 운영 전반에 필요한 기능까지 통합해 나갈 가능성이 높은 프로젝트입니다.

트러블슈팅

1. 면접 평가 도메인 ERD 설계

S

상황

TF에 합류했을 때 이미 여러 기능이 개발되어 있었고, 기능이 추가될 때마다 임의로 테이블이 늘어나며 쌓인 레거시 코드와 리팩토링이 필요한 코드가 많았습니다. 제가 개발하지 않은 도메인에 CS가 들어오면 바로 대응하기 어려운 상황도 자주 발생했습니다.

T

과제

TF 합류와 동시에 맡게 된 면접 평가 도메인을, 기존 정책과 플로우를 정확히 이해한 상태에서 무리 없이 확장 가능한 구조로 설계해야 했습니다.

A

행동

피그잼에 정리된 플로우를 분석하고, 노션에 기록된 기존 정책 문서를 확인했으며, 이미 정의돼 있던 API 인터페이스를 검토했습니다. 이를 바탕으로 부모 엔티티에 필요한 속성과 자식 엔티티로 분리했을 때의 장단점을 따져가며 ERD를 설계했습니다. 담당 외 도메인에 대한 CS는 기존 팀원에게 적극적으로 의존하며 협업으로 풀어나갔습니다.

R

결과

정책과 플로우에 대한 이해를 선행한 덕분에 큰 재설계 없이 안정적으로 확장 가능한 ERD를 설계할 수 있었습니다. 동시에, 레거시가 쌓인 프로젝트에서는 기존 팀원과의 협업과 지식 공유가 안정적인 설계만큼이나 중요하다는 것을 배웠습니다.

2. AssignedQuestionService upsert 로직 리팩토링

S

상황

개인 질문지 저장 API의 upsert 함수 안에 파트 잠금 여부 확인, 생성·수정·삭제 로직이 한꺼번에 몰려 있어 핵심 비즈니스 로직을 한눈에 파악하기 어려운 상태였습니다.

T

과제

이 로직을 팀의 아키텍처 컨벤션에 맞게, 책임이 명확히 분리된 구조로 리팩토링해야 했습니다.

A

행동

"무엇이 옳은가/허용되는가"를 판단하는 Policy와, 그 결정을 데이터에 적용하는 Applier로 역할을 분리했습니다. Applier 내부 함수도 생성 로직(createNewPartQuestion)과 수정·삭제 로직으로 다시 나눴습니다. 처음에는 데이터를 다루는 코드를 Policy에 넣었다가, 이름이 암시하는 책임과 실제 동작이 어긋난다는 것을 깨닫고 두 클래스의 역할을 재조정했습니다.

R

결과

"이름만 보고 책임을 추론했을 때 실제 책임과 일치하는가"를 체크하는 습관을 얻었고, 계층 분리는 단순한 코드 위치 이동이 아니라 데이터 흐름을 다시 설계하는 작업이라는 것을 배웠습니다.

배운 점 / 느낀 점

정책과 플로우를 충분히 이해한 뒤 설계에 들어가는 습관, 엔티티를 분리할지 합칠지 트레이드오프를 따지는 감각을 기를 수 있었습니다. 또한 이미 코드가 쌓인 프로젝트에 합류했을 때는 혼자 해결하려 하기보다 기존 팀원과 협업하는 것이 결과적으로 더 안정적인 서비스를 만든다는 것을 체감했습니다.
